---

## 1. 目标与非目标

### v1 目标
- **控制面端到端加密**:手机 App 与桌面桥之间的 JSON `/ws` 协议(会话列表、提示词、助手回复、思考过程、审批等)全程密文,**中继(hub / nginx / frp)只见密文**,无法解密。
- **一次性配对**:配对二维码可安全展示,**拍照/截屏无法重复绑定**。
- **逐设备密钥 + 可单独吊销**:每台设备独立密钥,丢失一台只吊销一台,且在 **hub 模式下也能吊销**(现状无此能力)。
- **硬切**:桥进入 E2EE 后拒收明文会话帧(防降级)。
- **前向兼容多设备/账号/商业化**:把设备建成"公钥身份",预留 `account` 字段,使后续账号归并、席位、服务器同步成为**叠加**而非重做。

### v1 非目标(明确推迟)
- `/file` 媒体(图片/视频)端到端加密 —— 仍走现有 token-gated 端点(nginx TLS 传输加密,hub 可见字节)。
- 服务器端账号体系、计费/席位、用服务器签发的一次性 challenge 替换全局 `HUB_AGENT_KEY`(独立商业化里程碑,见 §11)。
- 配对交换的前向保密(PSK 投递使用长期设备密钥接收,见 §6.3 限制)。
- 小程序。

## 2. 威胁模型

- **不信任中继**:hub(自托管或将来托管)、nginx、frp 均视为"诚实但好奇/可被攻陷",**不得**接触明文或 PSK。
- **不信任网络**:被动监听、重放在威胁内(故 v1 即含序号防重放)。
- **信任端点**:桌面机器(持 `~/.codex` 凭证,本就是 TCB)与已配对手机(持钥匙串)视为可信。
- **物理接近攻击**(攻击者实时偷拍屏幕上的二维码并抢先配对)不在 v1 重点防御内——一次性 `pairingId` + 首个完成者赢,可缓解照片**事后**重放;实时抢配对属于"看得到你屏幕"的近场威胁,与 happy 同级。

## 3. 已锁定的设计决策

| # | 决策 | 取舍 |
|---|---|---|
| D1 | 内容加密原语:**XChaCha20-Poly1305**(24B nonce,AEAD) | 两端一等公民,免 NaCl secretbox 的 XSalsa20 适配;不需与 happy 互通 |
| D2 | 范围:**仅控制面**,`/file` 推迟 | 性价比最高;媒体改造最贵 |
| D3 | **硬切**:配对后只收密文(首帧规则见 §7.4) | 防降级攻击 |
| D4 | **逐设备 PSK** | 与现有逐设备 token 吊销模型一致 |
| D5 | 配对:**一次性 ephemeral 封装**(happy 式) | 二维码无秘密、可作废、商业化可叠加 |
| D6 | **设备=长期公钥身份** + `account` 字段 | 前向兼容账号/多设备/服务器同步 |

## 4. 密钥层级(架构总览)

```
机器(桌面)
├─ 登记密钥对 enroll.{key,pub}    长期,NaCl box,证明"PSK 来自本机";配对时向手机封 PSK
├─ 路由 token                     长期,hub 可见,仅路由/限流;不再是机密边界
└─ devices.json                   keyId → { name, devicePub, account, psk }  0600

设备(手机)
├─ 设备身份密钥对 D.{pub,sec}      长期,存钥匙串;身份 + 接收 PSK 封装;将来被 account/K_content 寻址
└─ PSK(每设备)                   信道机密;HKDF 派生双向子密钥
```

要点:**身份(keypair)与信道机密(PSK)分离**。PSK 保护信道、可被机器轮换;`devicePub` 是稳定身份,将来 `seal(K_content → devicePub)` 直接寻址。

## 5. 数据格式

### 5.1 二维码载荷(v2,无任何秘密)
```json
{ "v":2, "machine":"mac-studio", "host":"relay.example.com",
  "token":"<路由 token,hub 可见>",
  "pairingId":"<一次性,TTL 5min>",
  "enrollPub":"<机器登记公钥 base64>" }
```

### 5.2 `devices.json`(机器,0600)
```json
[ { "keyId":"k7f3…", "name":"我的 iPhone",
    "devicePub":"<手机设备公钥 base64>",
    "account":"",
    "psk":"<base64 32B>",
    "added":"2026-06-08" } ]
```

### 5.3 `pending-pairings.json`(托盘写、桥监听消费,0600)
```json
[ { "pairingId":"…", "expiresAt":"2026-06-08T12:05:00Z" } ]
```

### 5.4 线缆封包(每帧;E2EE 会话期间线上只有它)
```json
{ "k":"<keyId>", "s":<seq>, "n":"<24B nonce b64>", "c":"<ciphertext b64>" }
```
- `k` 明文 keyId,仅用于桥选 PSK(非机密)。
- `n` 每帧 `crypto/rand` 随机 nonce。
- `s` 单调递增序号;**AAD = `keyId | dir | seq`**;桥拒收非递增 seq → 防重放。
- 解密失败 / keyId 未知 / seq 回退 → 断连。
- 明文还原即原有 `{"type":...}` 协议对象,**上层协议零改动**。

### 5.5 配对帧(明文,载荷仅公钥,不含秘密)
```json
// 手机 → 桥
{ "type":"pair_init", "pairingId":"…", "devicePub":"<手机设备公钥 b64>", "name":"我的 iPhone" }
// 桥 → 手机(成功)
{ "type":"pair_result", "sealed":"<box(enroll.key→devicePub): {keyId, psk}>" }
// 桥 → 手机(失败)
{ "type":"pair_error", "reason":"unknown|expired|consumed" }
```

## 6. 密码学核心

### 6.1 原语
- **XChaCha20-Poly1305**(Go `x/crypto/chacha20poly1305.NewX`;Dart `package:cryptography` 的 `Xchacha20.poly1305Aead`)。
- 配对封装:**NaCl box(Curve25519 + XSalsa20-Poly1305)**(Go `x/crypto/nacl/box`;Dart `pinenacl` 或 `cryptography` 的 X25519+secretbox 组合)。

### 6.2 密钥派生
```
k_p2b = HKDF-SHA256(psk, salt=keyId, info="codex-e2ee/v1/phone->bridge")
k_b2p = HKDF-SHA256(psk, salt=keyId, info="codex-e2ee/v1/bridge->phone")
```
双向各一把子密钥,避免双向共用密钥导致 nonce 复用风险。

### 6.3 配对封装(双向认证)
- 桥:`sealed = box(plaintext={keyId,psk}, recipientPub=devicePub, senderSec=enroll.key)`。
- 手机:`box.open(sealed, senderPub=enrollPub(来自 QR), recipientSec=D.sec)`。
- 性质:**只有持 `D.sec` 的手机能解**(机密);手机用 QR 里 `enrollPub` 验证 → **确认 PSK 来自真机器**(防中间人塞假 PSK)。
- **限制**:PSK 投递用长期 `devicePub` 接收,无前向保密(若 `D.sec` 将来泄露且攻击者录过该次交换,可还原该 PSK)。单次性由 `pairingId` 消费保证。前向保密列为后续加固。

## 7. 桥(server)接入

### 7.1 新增 `e2ee` 包
- `seal(plainJSON, key, seq) -> envelope`、`open(envelope, key, expectSeq) -> plainJSON`。
- 高内聚、可独立单测;两种模式共用。

### 7.2 四个收发接缝(已勘定)
| 位置 | 改动 |
|---|---|
| `internal/bridge/server.go` 直连读循环(`wsjson.Read`) | 读原始字节 → `open` → `json.Unmarshal` 进 `inbound` |
| `internal/bridge/server.go` 直连 `conn.write` 闭包 | `json.Marshal` → `seal` → 发文本帧 |
| `internal/bridge/agent.go` hub 入站 `message` | `f.Data`(envelope)→ `open` → 派发 |
| `internal/bridge/agent.go` hub 出站 `writeFrame` | `seal` 后塞进 `hubFrame.Data` |

### 7.3 hub 模式选钥
hub 只认机器 token、对 `msg.Data` 透传不解析,故桥**靠帧里明文 `keyId` 查 PSK**——无需握手状态机,无状态封包,重连免重握手。**逐设备吊销在 hub 模式首次可用**(删 `devices.json` 条目即失效)。

### 7.4 硬切 + 首帧规则
一条连接的**首帧**只允许两种:
1. 明文 `pair_init`(载荷仅公钥)→ 走配对握手 → 完成即断;
2. E2EE 封包帧 `{k,s,n,c}` → 正常会话。

其余明文一律丢弃断连。既保持"会话硬切"又放行公钥-only 的配对。

### 7.5 设备库与吊销
- 桥启动加载 `devices.json` → 内存 `keyId → {name, devicePub, account, psk}`;文件变更**热重载**(fsnotify 或 SIGHUP)。
- 直连模式下 **PSK 成为真正认证**(能解开并验签即已认证);token 退为路由/限流;`authDevice` 的设备名改由 `keyId → name` 提供。审批归属/审计沿用设备名。
- 吊销 = 删 `devices.json` 条目 + 重载 → 该设备帧再不可解。

### 7.6 配对处理(桥侧)
- 监听 `pending-pairings.json`;收到 `pair_init`:校验 `pairingId` 存在、未过期、未消费 → 现生成 `(keyId, psk)` → 写 `devices.json`(含 `devicePub`、`name`)→ 从 pending 删除(消费)→ 回 `pair_result`。
- 校验失败回 `pair_error`。

### 7.7 provision / 托盘
- `provision`(安装时):生成 `enroll.{key,pub}`(0600/0644)与路由 token。
- 托盘「配对新设备」:`crypto/rand` 生成 `pairingId`+TTL → 写 `pending-pairings.json` → 读 `enroll.pub` → 出 v2 二维码。**托盘保持无密码学**(只生成随机 id + 读公钥)。
- 托盘「管理/吊销设备」:列 `devices.json` 的 keyId+name,删一项即吊销(可 v1 最简,甚至先文档化为编辑文件+重载)。

## 8. Flutter(App)接入

- `models/machine.dart`:`Machine` + `keyId`;**`psk` 与设备私钥不进明文 JSON 列表**,单独存 `flutter_secure_storage`(钥匙串),key=`psk:<machineId>` / `devkey:<machineId>`。新增 `account` 透传字段。
- 配对:扫码(`qr_scan`/`connect_screen`)认 v2 载荷 → **生成长期设备密钥对**(存钥匙串)→ 连 hub(用 QR 路由 token)→ 发 `pair_init(devicePub)` → 收 `pair_result` → `box.open` 解 PSK → 存钥匙串。
- `services/bridge_client.dart` 加 codec(`package:cryptography`):`_send`(`:133`)出站 `seal` + 自增 seq;`_onData`(`:252`)入站 `open` + 校验 seq。两口与 Go 侧对称。
- `/file` 取图 URL(`:141-154`)**不变**(本轮不动媒体)。

## 9. 错误处理

- 解密/验签失败、未知 keyId、seq 回退 → 审计记录 + 断连(不泄露细节)。
- `pair_error` 在 App 提示"二维码已失效,请重新生成"。
- 热重载读 `devices.json` 失败 → 保留旧内存表 + 审计告警,不崩。
- 钥匙串读写失败(App)→ 进入未配对态,引导重新扫码。

## 10. 测试

- **Go 单测**:`e2ee` 包 round-trip;**跨端测试向量**(固定 psk/keyId/nonce/明文 → 期望密文),Dart 侧以同组向量断言互通;篡改密文/未知 keyId/seq 回退 → 必拒。
- **配对单测**:`pairingId` 有效/过期/已消费三态;`box` 封/解 + 错误 enrollPub 验签失败;消费后再用必拒。
- **桥单测**:E2EE 模式收明文会话帧 → 断连(硬切);`devices.json` 热重载;吊销后旧 keyId 失效。
- **手动联调**:Flutter 真机 ↔ 桥,直连 + hub 两条路;抓 hub 侧帧确认只见 `{k,s,n,c}` 与 `pair_*`(无明文会话内容、无 PSK)。

## 11. 商业化(后续独立里程碑,叠加)

选了 D5/D6 后,以下为**叠加**而非重做:

- **账号 = 客户持有的密钥对**(服务器零知识)。`devices.json.account` 归并同账号设备。
- **每机密钥对 + 服务器签发一次性 challenge** 替换全局 `HUB_AGENT_KEY`:机器注册改为"签名服务器下发的短 TTL 一次性 challenge"(规避 happy issue #669 的客户端自出 challenge 可重放问题);hub 只存 机器公钥 ↔ 账号。
- **服务端席位/吊销/计费**:hub 知 账号→机器→设备(皆公钥),可数席位、按订阅放行、全局吊销,**仍不碰明文/PSK**。
- **多设备共享会话同步**(若引入服务器内容同步):引入 `K_content`,`seal(K_content → devicePub)` 每设备各一份;加设备=多 wrap,吊销=删 wrap + 轮换 `K_content`。
